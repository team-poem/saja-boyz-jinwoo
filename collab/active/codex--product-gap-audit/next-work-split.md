# 다음 구현 분담 제안

2026-10-07. 기존 분담(우리 검색, amazon 목록·상세·제보)을 유지하되 이번 단위를 작게 잡는다. 상대의 새 claim/답변은 아직 확인되지 않았으므로 amazon 담당은 제안이며 착수 확정이 아니다.

## 우리: 키워드 검색의 첫 완결 흐름

범위: /search 입력 → URL q → 서버 /news keyword 조회 → 기존 ArticleList로 결과 표시. 검색어 수정/초기화·새로고침·뒤로가기, 로딩·빈 결과·실패 상태를 검증한다. 검색 전 안내와 결과 0건을 구분한다. 주소/좌표 검색이 아니라 명세가 제공하는 제목·설명 키워드 검색임을 UI에 명시한다.

예정 파일: src/app/search/, src/features/search/, src/features/article-list/api/fetch-articles.ts 및 신규 검색 테스트. API 함수에는 선택적 keyword를 추가하고 기본 호출은 현재 목록과 동일하게 유지한다. q는 프런트 URL 상태, keyword는 서버 요청 파라미터로 구분한다.

첫 PR 제외: 최근 검색 저장, 자동완성, 디바운스 실시간 검색, 카테고리/위치 필터, 페이지네이션, 지도 SDK, 상세·제보 구현. 존재하지 않는 기능을 작동하는 필터처럼 노출하지 않는다.

승인용 테스트 초안의 항목: 입력 및 제출 URL 인코딩, 공백 검색어 처리, keyword 전달과 기존 무인자 목록 동작 보존, 정상/빈/실패 결과, URL 재진입·뒤로가기 동기화. 구체적인 테스트 코드는 sobaya 초안으로 별도 준비 후 승인받는다.

## amazon에게 제안: 서버 계약 확인과 상세 준비

1. keyword 검색 범위·공백·특수문자, offset/limit 기본값·상한, 정렬과 total/중복 기준을 서버 구현과 대조해 문서화.
2. article_id 단건 조회가 가능한지 확인. collections/{id}와 기사 ID를 혼동하지 않는다. 없으면 상세 구현에 필요한 최소 응답/API를 제안.
3. 이 정보를 바탕으로 목록→상세 흐름의 별도 claim과 인수 조건을 준비. API가 준비되기 전 상세 완료를 약속하지 않는다.

## 충돌 방지와 통합 순서

- 검색 개발 중 fetch-articles.ts는 우리 수정 담당으로 제안한다. amazon은 이 파일 변경 전 reply로 조율하며, 현재 문서는 실제 잠금이나 상대 승인으로 취급하지 않는다.
- 두 작업의 구현 claim을 만들기 직전에 digest를 다시 확인한다. 동료가 동일 파일을 편집 중이면 먼저 조율한다.
- 기본 API 호출·기존 목록·오류 경계·이미지 계약을 보존하는 검색 PR을 dev에 먼저 리뷰한다. 이후 amazon의 목록/상세 PR은 머지된 dev 기준으로 시작한다.
- 서버 계약 조사는 검색 UI 초안 준비와 병행할 수 있다. 서버 계약이 현재 가정과 다르면 구현 전에 승인 기준을 재검토한다.
- GitHub 코멘트는 초안 승인 후에만 게시하고 계정은 amazon7737을 사용한다.
